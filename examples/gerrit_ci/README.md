# OpenCodeReview - Gerrit CI 演示

此演示展示了如何将 OpenCodeReview 集成到 [Gerrit](https://www.gerritcodereview.com) 代码审查流程中，以自动审查更改并将发现的问题作为补丁集上的内联评论以及摘要消息发布。

与 GitHub Actions、GitLab CI 和 GitFlic 示例类似，发布粘合代码位于 CI 层，而不是 `ocr` 二进制文件中。这里是一个小型、无依赖的 Python 脚本——[`post_review.py`](post_review.py)——它读取 `ocr review --format json` 的输出，并将其作为**一个批量的 ReviewInput** 发布到 Gerrit 的 set-review 端点，从而以原子方式完成审查：按文件分组的内联评论加上摘要消息，在单个请求中完成。

## 工作原理

```
Gerrit 触发器（补丁集创建）→ Jenkins 任务 → ocr review --format json → post_review.py → POST /a/changes/{change}/revisions/{revision}/review
```

1. Gerrit 触发器插件在 `patchset-created` 事件上触发 Jenkins 任务
2. 该任务获取更改引用并运行 `ocr review --format json --audience agent`
3. `python3 post_review.py` 读取 JSON 并 POST 一个包含以下内容的单个 `ReviewInput`：
   - 更改行上的**内联评论**，按文件分组
   - 包含总计的**摘要消息**（以及任何无法内联放置的评论）

该脚本为您处理 Gerrit 特有的棘手问题：对 `/a/` 端点的预emptive HTTP 基本认证、响应上的 `)]}'` 反 XSSI 前缀、实际为 HTML 登录页面的 200 响应（视为配置错误），以及批处理时的 HTTP 400（重试一次，将所有内联评论折叠到摘要消息中，以便发现的问题仍能到达更改）。

## 设置

### 1. 创建机器人账户和 HTTP 密码

为机器人创建一个专用的 Gerrit 账户（其名称将显示在审查评论上）。以该账户登录，并在 **设置 → HTTP 凭据 → 生成密码** 下生成令牌。

> **重要提示：** 此 HTTP 密码**不是**账户/登录密码——使用登录密码是从 `/a/` 端点收到 HTTP 401 的最常见原因。当 Gerrit 拒绝凭据时，`post_review.py` 会明确说明这一点。

### 2. 授予最小权限

机器人只需要读取更改并对其进行评论。在项目（或 `All-Projects`）的访问设置中，授予机器人组对 `refs/*` 的**读取**权限——评论开放的更改不需要更多权限。除非您启用标签投票（请参阅注释），否则不要授予 `Label: Code-Review` 投票权。

### 3. 配置流水线

将 `post_review.py` 复制到您的仓库中（或在任务中获取它），并将其接入您的 Jenkins 任务——请参阅此目录中的 [`Jenkinsfile`](Jenkinsfile)。将 `GERRIT_HTTP_USER` / `GERRIT_HTTP_PASSWORD` 存储为 Jenkins 凭据，以及审查步骤本身的 LLM API 令牌。`ocr` 直接从环境中解析 `OCR_LLM_URL` / `OCR_LLM_TOKEN` / `OCR_LLM_MODEL`——无需 `ocr config set`，因此令牌永远不会写入共享代理上的磁盘。

## 配置参考

每个值都可以通过标志或环境变量传递；**标志覆盖环境变量**。运行 `python3 post_review.py -h` 可查看相同列表。

| 标志 | 环境变量回退 | 默认值 | 描述 |
|------|--------------|---------|-------------|
| `--gerrit-url` | `GERRIT_URL`，否则从 `GERRIT_CHANGE_URL` 派生 | — | Gerrit 基础 URL（保留上下文路径，容忍尾部斜杠） |
| `--change` | `GERRIT_CHANGE_NUMBER` | — | 更改编号 |
| `--revision` | `GERRIT_PATCHSET_REVISION` | `current` | 要评论的修订/补丁集 |
| `--user` | `GERRIT_HTTP_USER` | — | HTTP 凭据用户名 |
| `--password` | `GERRIT_HTTP_PASSWORD` | — | Gerrit HTTP 密码，**不是**账户密码 |
| `--input` | — | `-`（标准输入） | 审查结果 JSON 文件（`-` = 标准输入）；也可作为位置参数接受，如果两者都给出，则位置参数优先 |
| `--dry-run` | — | 关闭 | 打印 ReviewInput 而不是发布它 |
| `--timeout` | — | `30` | HTTP 超时时间（秒） |

`GERRIT_CHANGE_URL` 派生：现代更改 URL（`{base}/c/{project}/+/{number}`）在 `/c/` 处分割，保留任何上下文路径；旧版 URL（`{base}/{number}`）则去掉尾部的数字。

## 用法

### Jenkins（Gerrit 触发器）

请参阅此目录中的 [`Jenkinsfile`](Jenkinsfile)。Gerrit 触发器插件将 `GERRIT_CHANGE_NUMBER`、`GERRIT_PATCHSET_REVISION` 和 `GERRIT_CHANGE_URL` 注入构建环境，因此脚本无需位置参数接线：

```bash
ocr review --format json --audience agent | python3 post_review.py
```

### 其他触发器

该脚本与触发器无关：任何能设置上述环境变量（或传递标志）的工具都可以驱动它。

- **Zuul** — 可以在 Zuul 任务中从 `zuul.change` / `zuul.patchset` 变量设置相同的环境契约；脚本不关心是谁导出的。
- **`patchset-created` 钩子** — 直接从服务器端钩子发布：

  ```bash
  ocr review --format json | python3 post_review.py \
    --gerrit-url https://gerrit.example.com --change "$CHANGE" --revision "$REVISION"
  ```

## 试运行

在不影响更改的情况下本地测试发布步骤（无需凭据）：

```bash
ocr review --from origin/main --to HEAD --format json > /tmp/r.json
python3 post_review.py /tmp/r.json --dry-run     # 或：--input /tmp/r.json
```

`--dry-run` 打印将要 POST 的确切 ReviewInput：

```json
{
  "message": "OpenCodeReview 在审查的 1 个文件中发现 2 个问题；2 个已作为内联评论发布。",
  "tag": "autogenerated:opencodereview",
  "notify": "OWNER",
  "omit_duplicate_comments": true,
  "comments": {
    "internal/scan/scan.go": [
      { "message": "**严重性：** 高 · ...", "unresolved": true, "line": 42 },
      ...
```

## 注意事项与限制

- **重新审查和重复** — ReviewInput 设置了 `omit_duplicate_comments`，但 Gerrit 只删除**字节完全相同**且位于相同位置的评论。新的 LLM 运行通常会改写其发现，因此重新触发的审查**将会**重复评论。所有机器人评论都带有 `autogenerated:opencodereview` 标签，因此 UI 和脚本可以过滤或折叠它们。
- **重试** — 仅在可证明**未**应用审查的失败时重试 POST（最多 `MAX_ATTEMPTS` 次，采用指数退避）：HTTP 5xx 和响应前连接错误（拒绝/重置/DNS）。读取超时**不**重试——它们是不明确的（服务器可能已应用审查），且 `omit_duplicate_comments` 不会对摘要 `message` 去重，因此重试可能发布重复的更改消息。4xx 响应（400/401/404/409）不重试；它们会被分类并直接处理。
- **原生修复建议和标签投票** — 有意保留的未来选项。`fix_suggestions`（Gerrit 的原生应用修复功能）在 Gerrit 3.10+ 中受实验性门控，并且需要此示例不携带的字符级范围，因此建议代码在普通围栏代码块中以 `**Suggestion:**` 标题输出，可在任何 Gerrit 版本上可移植地渲染。标签投票（Code-Review ±1）同样不在 v1 中——请参阅下面的**标签投票**。
- **标签投票** — 有意不在 v1 中：脚本只评论，不投票。需要门控的团队可以在 `build_review_input` 中的 ReviewInput 中添加一行：`"labels": {"Code-Review": -1}`（并授予机器人标签权限）。
- **修订竞争** — 始终传递触发器注入的修订 SHA（`GERRIT_PATCHSET_REVISION`）。`current` 默认值仅用于手动运行：如果在流水线中途有新补丁集落地，`current` 会将评论重新定位到审查从未见过的代码上。
- **退出代码** — 成功时为 `0`（HTTP 409 更改已关闭也被容忍并退出 0）；输入 JSON 不可读或无法解析时为 `1`；配置或 HTTP 错误时为 `2`，以便 CI 步骤可见地失败。409 处理是防御性的：现代 Gerrit（在 3.14 上验证）即使对已放弃的更改也接受无标签审查，因此它主要对较旧/更严格的服务器很重要。
